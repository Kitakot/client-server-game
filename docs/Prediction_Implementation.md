## Адаптация задания

Вместо Unreal используется Unity, вместо непрерывной ходьбы — приказы юниту
на клеточной карте. Действие с ограничением повторного использования — марш.
Сервер запускается отдельным C++-процессом, два игрока — отдельными клиентами.
Это Dedicated Server, а не Listen Server. Аналог Saved Moves — очередь `pending`.
Встроенный CharacterMovementComponent не используется: повторное применение
дискретных приказов реализовано в клиенте явно.

## Правила

Карта 6×6, игроки 0 и 1, начальные позиции (0,0) и (5,5), препятствие (2,0).
Первым ходит игрок 0. В начале своего хода юнит получает 3 AP.
Шаг стоит 1 AP и перемещает на одну клетку. Марш стоит 2 AP и перемещает
на две клетки. Проверяются промежуточная и конечная клетки.
После марша `marchReadyTurn = turn + 4`: повтор возможен через два собственных
хода. Завершение хода переключает игрока и увеличивает глобальный `turn`.

Сервер проверяет игрока, номер хода, действие, направление, границы, препятствия,
занятость, AP и перезарядку. До завершения проверок движение не меняет состояние.

## Поток данных

```text
Ввод → inputId/turn/action/dx/dy → pending → локальное предсказание (если включено)
                               ↓
                      TURN_INPUT → C++-сервер
                               ↓
                проверка порядка и правил → принятие/отказ
                               ↓
                  WORLD_STATE + processedInput
                               ↓
         удалить обработанные → принять серверную базу → replay pending
```

Клиент передаёт намерение, а не готовые координаты. Сервер связывает игрока
с endpoint, назначенным при HELLO. `inputId` начинается с 1 для каждого игрока.
Обрабатывается только следующий ожидаемый номер; дубликаты и преждевременные
номера пропускаются. Клиент повторяет очередь каждые 200 мс.

Отказ по игровым правилам тоже продвигает `processedInput`. Невалидная датаграмма
его не продвигает. Снимки рассылаются после обработанных приказов и примерно
каждые 100 мс. Они содержат полный мир и индивидуальное подтверждение игрока.
`result` относится только к последнему обработанному приказу данного игрока.

Клиент отбрасывает старые ревизии, принимает серверное состояние и повторно
рассчитывает неподтверждённые приказы. При выключенном CSP он ждёт снимка.
При включённом — отображает ожидаемый результат сразу. Авторитетным остаётся
серверный мир. При отсутствии снимков более 5 секунд новый ввод блокируется;
повторная отправка уже ожидающих приказов продолжается. Очередь ограничена 32.

## Отличие от ПР №3

`ReliableChannel` и `OrderBook` относятся к старым UNIT_MOVE/UNIT_ATTACK.
ACK подтверждает доставку и не доказывает допустимость действия. Unity использует
`processedInput` и состояние из снимка. Старые команды работают с отдельными
демонстрационными данными и не изменяют `prediction::Match`.

### Запуск сервера и двух клиентов

Из корня репозитория собрать и запустить сервер:

```powershell
cmake -S . -B build
cmake --build build --config Debug --target server
.\build\Debug\server.exe
```

Для одноконфигурационного генератора executable может находиться в build/server.exe.
Консоль сервера оставить открытой; ожидается сообщение о порте 54000.

1. В Unity Hub открыть папку unity-client редактором версии из
   ProjectSettings/ProjectVersion.txt. Дождаться импорта и компиляции.
2. Открыть Assets/Scenes/PredictionLab_1.unity.
3. До Play выбрать активный PredictionClient: Server Ip = 127.0.0.1,
   Server Port = 54000, Prediction Enabled включён, Debug Ignore Obstacle выключен.
4. NetworkLab оставить выключенным. Сохранить сцену.
5. Нажать Play, открыть вкладку Game и нажать Connect. Первый клиент должен
   получить Player: 0, Turn: 1, active player: 0, pending: 0.
6. Для второго клиента создать Windows-сборку через File → Build Profiles,
   включив PredictionLab_1 в список сцен. Запустить executable и нажать Connect.
7. Проверить Step up игроком 0: после подтверждения (0,1), AP=2 на обоих клиентах.
   Нажать End turn и продолжить игроком 1.

Если при подготовке сборки клиент уже подключался, перед окончательным запуском
двух клиентов перезапустить сервер: старый слот сам не освобождается.
Можно также использовать две копии desktop-сборки вместо Editor и сборки.

**Состояние файлов при актуализации:** в сохранённой сцене порт уже 54000,
но инициализатор serverPort в PredictionClient.cs остаётся 54010. Для существующей
сцены используется сериализованное значение Inspector; новый компонент необходимо
настроить на 54000. Изменения Inspector выполнять вне Play Mode.

Управление — экранными кнопками; Cube не связан с состоянием юнита.
При постоянном Connecting проверить порт и сборку сервера; unknown packet type
в его логе указывает на отсутствие поддержки новых сообщений в запущенной сборке.
При No server snapshots проверить приём периодических снимков. Красные ошибки
компиляции Unity нужно устранить до запуска сцены.

### Сравнение и намеренное расхождение

Для сравнения выполнить Step up из новой сессии при Lag 100 мс и Drop 0%,
сначала без Prediction, затем с Prediction. При каждом запуске сохранить
видео нажатия, локального отклика и подтверждения.

Для коррекции при Lag 175 мс и Drop 5% включить Prediction и
`DEBUG: ignore obstacle locally`, затем выполнить March right из (0,0).
Ожидается локальное (2,0), AP=1; сервер возвращает Blocked, (0,0), AP=3.
После снимка клиент восстанавливает позицию и AP. Флаг не передаётся серверу.

Для replay добавить Step up, пока марш ожидает подтверждения. Итог после
обработки обоих приказов — (0,1), AP=2. Для доказательства именно replay
зафиксировать `REPLAY` после снимка первого приказа при ещё ожидающем втором.
Снимок, подтверждающий сразу оба приказа, показывает итог, но не промежуточный replay.

`PROCESSED elapsedMs` — время от отправки до получения подтверждающего снимка,
а не задержка первого визуального отклика. Последнюю измеряют по записи.
`CORRECTION` сравнивает предыдущее отображение с пересчитанным состоянием;
само наличие строки не является отдельным измерением сетевой задержки.

## Материалы и ограничения

Записи `baseline_no_prediction`, `prediction_enabled`, `correction_example`
пока не приложены. Правила размещения: [media/README.md](media/README.md).
Архив тестовых исходников не заменяет лог запуска или видео.

- Нет аутентификации, защиты от подмены endpoint и идентификатора сессии.
- Два слота не освобождаются; для новой сессии перезапускаются сервер и клиенты.
- Третий клиент остаётся без регистрации; отдельного ответа SERVER_FULL нет.
- Счётчики и сравнения ревизий рассчитаны на короткую сессию без переполнения.
- Полные снимки, фиксированный интервал повторов, без адаптивного RTO для Unity.
- Карта текстовая, визуального сглаживания и связи Cube с состоянием юнита нет.
- Unity-сборка и ручная демонстрация требуют отдельной проверки.
