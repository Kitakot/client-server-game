## Реализация

| Компонент | Файл | Назначение |
|---|---|---|
| Формат сообщений | [replication_lab.hpp](../protocol/replication_lab.hpp) | Режимы, объекты, сериализация и ACK |
| Сервер эксперимента | [prediction_lab.hpp](../server/prediction_lab.hpp) | Класс ReplicationLab, рассылка, версии, CSV |
| Точка входа | [main.cpp](../server/main.cpp) | Аргументы `--replication` и вызов Tick |
| Клиент Unity | [ReplicationLabClient.cs](../unity-client/Assets/Scripts/ReplicationLabClient.cs) | Приём, отображение, подтверждение версий |
| Сцена | [ReplicationLoad.unity](../unity-client/Assets/Scenes/ReplicationLoad.unity) | Сцена опыта с префабом объектов |
| Анализ | [compare_replication.py](../tools/compare_replication.py) | Графики и сводная таблица |

Историческое имя серверного файла `prediction_lab.hpp` сохранено; именно в нём
находится `ReplicationLab`. Эксперимент использует UDP **54020**. Старый игровой
сервер продолжает слушать **54000**, поэтому его сообщения JOIN и INPUT
не означают подключения к эксперименту ПР5.

Сервер хранит авторитетное состояние и отдельные подтверждённые версии объектов
для каждого клиента. Клиент применяет только более новую версию и отправляет ACK
для каждого корректного сообщения, включая повторное. Старый пакет не откатывает
объект. В dirty-режимах подтверждённая текущая версия больше не отправляется;
неподтверждённая повторяется не раньше чем через 300 мс. Новая версия может быть
отправлена на следующем проходе рассылки без ожидания этого таймера.

## Сценарий и режимы

Эксперимент запускается после HELLO от двух различных endpoint и длится 60 секунд.
В мире 64 объекта: 56 объектов карты и 8 юнитов. Начальная позиция объекта с
номером `id`: `(id % 8, id / 8)`, начальная версия — 1.

На условных ходах 1–55, один ход в секунду, каждый юнит получает
`x = (id % 8 + turn) % 16`; версия увеличивается. На ходах 10, 20, 30, 40 и 50
объекты карты 0–4 по очереди сдвигаются по Y на одну клетку. Последние пять
секунд предназначены для доставки и подтверждения конечного состояния.
Рассылка планируется раз в 100 мс; реальная частота зависит от выполнения цикла.

| Режим | Отправка | Формат одного объекта с прикладным заголовком |
|---|---|---:|
| baseline | Все объекты на каждом проходе | FULL, 28 байт |
| quantized | Все объекты на каждом проходе | COMPACT, 17 байт |
| dirty | Только неподтверждённые текущие версии | FULL, 28 байт |
| optimized | Только неподтверждённые текущие версии | COMPACT, 17 байт |

FULL хранит координаты как целые числа в тысячных долях клетки. COMPACT хранит
целочисленные координаты клетки по одному байту и сокращает поля id и kind.
Для данного диапазона сетки это преобразование без потери точности. Подробности
сообщений приведены в [спецификации протокола](Protocol_Specification.md#13-протокол-репликации-пр-5).

## Запуск

Команды выполняются из корня репозитория. Для существующей конфигурации Visual
Studio с каталогом Debug:

```powershell
cmake -S . -B build
cmake --build build --config Debug --target server
New-Item -ItemType Directory -Force docs/replication
.\build\Debug\server.exe --replication baseline docs/replication/baseline.csv
```

Повторный запуск с тем же путём перезаписывает CSV. Сохраняйте новые измерения
под отдельными именами или предварительно сохраняйте прежние результаты.

1. Открыть проект `unity-client` в Unity; версия проекта — 6000.4.0f1.
2. Открыть `Assets/Scenes/ReplicationLoad.unity`. Проверить активный
   `ReplicationLabClient`, назначенный `objectPrefab`, IP `127.0.0.1` и порт `54020`.
3. В **File → Build Profiles → Scene List** включить `ReplicationLoad` первой
   сценой либо оставить её единственной и собрать Windows-клиент.
4. Запустить два экземпляра этой сборки либо Editor и один экземпляр сборки.
5. В обоих клиентах нажать **Connect replication client**.
6. Дождаться завершения 60 секунд, проверить `Objects: 64/64` и
   `Final scenario state: True` на обоих клиентах, сохранить снимки экрана.
7. Проверить `end_ok` в CSV. Завершить сервер и клиентов перед следующей серией.

В отслеживаемом `EditorBuildSettings.asset` пока указана `PredictionLab_1.unity`.
Старая сборка с кнопками Step/End turn и надписью Prediction относится к ПР4.
Нужна пересборка с правильной сценой: смена одного порта у PredictionClient
не делает его совместимым с протоколом ПР5.

Ожидаемые сообщения сервера:

```text
[REPLICATION] mode=baseline port=54020 waiting for two clients
[REPLICATION] client=0 ...
[REPLICATION] client=1 ...
[REPLICATION] measurement started
[REPLICATION] finished, final state acknowledged=1
```

Команды для остальных независимых запусков:

```powershell
.\build\Debug\server.exe --replication quantized docs/replication/quantized.csv
.\build\Debug\server.exe --replication dirty docs/replication/dirty.csv
.\build\Debug\server.exe --replication optimized docs/replication/optimized.csv
.\build\Debug\server.exe --replication optimized docs/replication/optimized_loss5.csv
```

Каждая команда запускает отдельную серию; предыдущий процесс нужно завершить.
`optimized_loss5` — имя файла эксперимента, режим сервера остаётся `optimized`.
Потери задаёт внешний эмулятор, аргумент сервера их не включает. Для повторения
серии с потерями необходимо отдельно записать версию эмулятора, направления,
фильтр, процент потерь и задержку. Эти настройки в текущих CSV не сохраняются.

## Построение графиков

```powershell
python -m pip install matplotlib
python tools/compare_replication.py
```

Для открытия окон графиков:

```powershell
python tools/compare_replication.py --show
```

Выбор входного каталога, выходного каталога и интервала агрегации:

```powershell
python tools/compare_replication.py --input-dir docs/replication --output-dir docs/replication/graphs --bin-seconds 1
```

Скрипт читает каждый CSV как отдельную серию и сохраняет её имя, поэтому
`optimized` и `optimized_loss5` не объединяются. Повреждённые и незавершённые
файлы пропускаются с пояснением. Если пригодных серий нет, код возврата — 1.
`end_unconfirmed` допускается в сравнении с отметкой `*`; это не подтверждение
корректности конечного состояния. Экономия рассчитывается относительно файла
`baseline.csv` с режимом baseline и статусом end_ok; без него поле пустое.

Результаты сохраняются в `docs/replication/graphs`, существующие графики и
сводная таблица при повторном запуске обновляются:

- [traffic.png](replication/graphs/traffic.png): скорость по интервалам и накопленный объём.
- [comparison.png](replication/graphs/comparison.png): средняя скорость и количество сообщений в секунду.
- [object_types.png](replication/graphs/object_types.png): объём для объектов карты и юнитов.
- [summary.csv](replication/graphs/summary.csv): численные результаты всех серий.

## Методика расчёта

CSV содержит поля `mode,event,time_s,client,object_id,kind,bytes`.
`start` отмечает начало измерения, `send` — успешную отправку через серверный
сокет, `end_ok` или `end_unconfirmed` — завершение. Успешная отправка через сокет
сама по себе не гарантирует доставку клиенту.

Суммируются байты строк send, включая повторы и отправки обоим клиентам.
В `bytes` входят 8 байт прикладного заголовка. HELLO, входящие ACK и заголовки
IP/UDP не включены. Это измерение исходящего прикладного трафика репликации,
а не всего сетевого обмена. KB означает 1000 байт.

```text
B = сумма bytes по send
N = число строк send
T = time_s маркера завершения
Средняя скорость = B / T / 1000, KB/s
Средняя частота = N / T, сообщений/с
Экономия = (1 - скорость_серии / скорость_baseline) * 100%
```

На графике скорости байты суммируются по интервалам `--bin-seconds` и делятся
на длительность соответствующего интервала. Последний неполный интервал
использует свою фактическую длину; интервалы без отправок имеют нулевую скорость.

## Результаты

Источник — сохранённые CSV, обработанные `compare_replication.py`. Все серии
длились 60 секунд и завершились end_ok.

| Серия | Сообщений | Байт | Среднее, KB/s | Сообщений/с | Экономия к baseline |
|---|---:|---:|---:|---:|---:|
| [baseline](replication/baseline.csv) | 70 400 | 1 971 200 | 32,853 | 1173,333 | 0,00% |
| [quantized](replication/quantized.csv) | 70 400 | 1 196 800 | 19,947 | 1173,333 | 39,29% |
| [dirty](replication/dirty.csv) | 1 018 | 28 504 | 0,475 | 16,967 | 98,55% |
| [optimized](replication/optimized.csv) | 1 018 | 17 306 | 0,288 | 16,967 | 99,12% |
| [optimized_loss5](replication/optimized_loss5.csv) | 1 157 | 19 669 | 0,328 | 19,283 | 99,00% |

![Сравнение режимов](replication/graphs/comparison.png)

Число сообщений в baseline и quantized одинаково. Уменьшение размера с 28 до
17 байт даёт `(1 - 17/28) * 100% = 39,29%`, что совпадает с измерением.

Dirty убирает повторную передачу неизменных подтверждённых объектов. В серии
без дополнительных отправок получается `2 * (64 + 8 * 55 + 5) = 1018` сообщений:
начальное состояние, перемещения восьми юнитов и пять изменений объектов карты.
Именно столько записано в dirty и optimized. Combined-режим optimized дополнительно
сокращает каждое сообщение до 17 байт.

![Динамика трафика](replication/graphs/traffic.png)

В optimized_loss5 на 139 сообщений и 2363 байта больше, чем в optimized:
объём вырос примерно на 13,65%. Результат согласуется с дополнительными
повторными отправками, но сам CSV не содержит номера версии в каждой строке
send и журнала потерь. По нему нельзя восстановить точный процент потерь или
разделить потерянные данные и ACK. Название серии обозначает профиль опыта,
а не независимое доказательство настроек эмуляции.

![Объём по типам объектов](replication/graphs/object_types.png)

Высокая экономия объясняется выбранной нагрузкой: 56 из 64 объектов почти
не меняются, а baseline рассылает весь мир примерно десять раз в секунду.
Результат 99,12% относится к этому сценарию и одному прогону каждого режима.
Он не доказывает такое же сокращение во всей будущей 4X-игре. Повторные серии
и разброс результатов пока не представлены.

## Проверки и ограничения

Подтверждено артефактами: пять завершённых CSV с end_ok, успешная обработка
скриптом, сводная таблица и три PNG. end_ok означает, что на момент завершения
сервер получил от обоих клиентов ACK текущих версий всех объектов.
Это не заменяет проверку отображения и ожидаемых конечных координат в Unity.

| Проверка | Текущий статус |
|---|---|
| Подтверждение текущих версий обоими клиентами | end_ok во всех пяти CSV |
| Финальная сцена на обоих клиентах | В коде есть FinalStateMatches; снимки экрана к этим сериям не приложены |
| C++-тесты репликации | Пять TEST_CASE в [test_replication_lab.cpp](../tests/test_replication_lab.cpp), файл не включён в цель tests в CMakeLists.txt |
| Unity-тесты кодека | ReplicationCodecTests.cs содержит пустой класс |
| Автоматическая проверка потерь, повторов и перестановки пакетов | Результаты отдельного тестового прогона не представлены |

Для завершения проверки тестировщику нужно подключить файл C++-тестов к цели
tests, выполнить сборку и CTest, реализовать Unity-тесты кодека и сохранить
результаты. Обычный успешный CTest текущей конфигурации не подтверждает запуск
тестов репликации.

В этой реализации нет фильтрации видимости, тумана войны, пространственного
индекса или Replication Graph. Все 64 объекта доступны обоим клиентам. Сервер
по-прежнему обходит весь мир при рассылке, поэтому уменьшение сетевого трафика
не означает устранения стоимости обхода. Отдельного механизма dormancy нет:
эффект молчания статических объектов достигается проверкой версии и ACK.

Нет идентификатора сессии, аутентификации, освобождения слотов и полноценного
переподключения. Для новой серии перезапускаются все участники. Промежуточные
версии могут быть пропущены: передаётся актуальное состояние, а не надёжная
история всех игровых событий. При длительной остановке серверного процесса
проверка лимита 60 секунд может произойти до выполнения оставшихся условных
ходов; поэтому полезна независимая проверка FinalStateMatches в Unity.

## Работа команды

Распределение относится к обязанностям; персональное авторство коммитов этим
документом не устанавливается.

| Роль | Реализованная часть | Что подготовить для защиты |
|---|---|---|
| Разработчик сервера | Четыре режима, версии, ACK, повтор, сценарий, CSV | Показать Tick, AdvanceTurn, EncodeEntity и обработку ACK |
| Разработчик игрового клиента | Unity-сцена, декодирование, объекты, ACK, финальная проверка | Правильная сборка и демонстрация двух клиентов |
| Тестировщик | Данные пяти серий присутствуют в репозитории | Настройки эмулятора, снимки конечного состояния, запуск подключённых тестов |
| Автор документации | Описание протокола, запуска, результатов и графиков | Объяснить формулы, вывод и ограничения |
