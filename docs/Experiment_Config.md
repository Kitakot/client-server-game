## Серии

| Серия | Настройки Clumsy |
|---|---|
| baseline | Clumsy выключен |
| delay_50 | Lag 50 мс |
| delay_100 | Lag 100 мс |
| jitter | Lag 50 мс + Throttle 100 мс 50% |
| loss_5 | Drop 5% |
| combined | Lag 100 мс + Throttle 100 мс 50% + Drop 5% |

## Обоснование тайм-аута
1000 мс: максимальная вносимая задержка в сериях около 150–250 мс, запас в
несколько раз исключает ложные тайм-ауты; при этом интервал 200 мс означает,
что одновременно в ожидании не больше ~6 пакетов.

## ПР №3: надёжная доставка

| Параметр | Значение |
|---|---|
| Клиент | `reliable_client`, 50 приказов (UNIT_MOVE / UNIT_ATTACK через один) |
| Интервал | 200 мс |
| max_attempts | 5 |
| RTO | адаптивный, [100, 3000] мс, начальный 1000 мс, 5 PING разогрева |
| Фильтр Clumsy | `outbound and (udp.DstPort == 54000 or udp.SrcPort == 54000)` — обе стороны |
| Сервер | перезапускался перед каждой серией |

| Серия | Настройки Clumsy |
|---|---|
| baseline | выключен |
| loss_5 | Drop 5% |
| loss_10 | Drop 10% |
| loss_20 | Drop 20% |
| delay_100_loss_5 | Lag 100 мс + Drop 5% |
| jitter_loss_10 | Lag 50 мс + Throttle 100 мс 50% + Drop 10% |

Потери и задержка применяются к каждому направлению, поэтому вероятность
потерять приказ или его ACK за одну попытку равна 1 − (1 − p)², а Lag 100 мс
добавляет к RTT около 200 мс.

## ПР №4: Unity, предсказание и коррекция

Это план воспроизводимых экспериментов; фактические результаты и артефакты
вносятся в [Prediction_Test_Matrix.md](Prediction_Test_Matrix.md) после проверки.

| Параметр | Значение |
|---|---|
| Сервер | C++ `server`, UDP 54000 |
| Клиенты | Unity Editor и отдельная Windows-сборка |
| Unity проекта | 6000.4.0f1; для записи зафиксировать фактическую версию сборки |
| Сцена | Assets/Scenes/PredictionLab_1.unity |
| Объекты | PredictionClient включён, NetworkLab выключен |
| Адрес на одной машине | 127.0.0.1:54000 |
| Эмулятор | Clumsy; записать фактически использованную версию |
| Фильтр | `outbound and (udp.DstPort == 54000 or udp.SrcPort == 54000)` |
| Период снимков | Примерно 100 мс, также после обработки приказов |
| Повтор приказов/HELLO | 200 мс |
| Максимум pending | 32 |
| Порог отсутствия снимков | Более 5 с: блокировка нового ввода |

| Профиль | Lag в каждом направлении | Drop |
|---|---:|---:|
| P0 | Выключен | Выключен |
| P1 | 100 мс | 0% |
| P2 | 175 мс | 5% |

P1 добавляет примерно 200 мс к RTT, P2 — примерно 350 мс без учёта потерь,
повторов и обработки. 175 мс — фиксированная задержка внутри требуемого
диапазона 150–200 мс; джиттер этим профилем не задаётся.
Встроенные параметры LabUdp относятся к выключенному JSON-прототипу и
не эмулируют сеть активного PredictionClient.

### Порядок эксперимента

1. Перезапустить сервер и оба клиента; первый подключившийся получает игрока 0.
2. Проверить соединение без эмуляции и значения Player/Turn/Pending.
3. Включить профиль; записать настройки Clumsy и идентификатор сборки.
4. Для сравнения выполнить один Step up без CSP, затем из новой сессии с CSP.
5. Для коррекции включить CSP и debugIgnoreObstacle, выполнить March right
   из (0,0). Ожидается восстановление (0,0), AP=3 после Blocked.
6. Для replay добавить Step up до подтверждения марша. Итог — (0,1), AP=2;
   промежуточный replay подтверждать отдельной последовательностью логов.
7. Сохранить запись, логи и фактический результат. Отключить эмуляцию после серии.

`PROCESSED elapsedMs` измеряет время до подтверждающего снимка.
Время первого визуального отклика измеряется отдельно по видео.
